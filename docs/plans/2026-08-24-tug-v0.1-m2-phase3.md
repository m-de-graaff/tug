# tug v0.1 «Hull» — Phase 3 «Loop + event bus» Implementation Plan

> **To execute:** use the `executing-plans` skill. Steps use `- [ ]` for tracking.

**Goal:** Ship Phase 3 of `.artifacts/v0.0.md` — one blocking loop with zero
busy-waiting, one wakeup mechanism, a typed event bus in `tugcore`, and a render
scheduler with a frame budget — and close the carried-forward `--caps` defect,
which is blocked on the same `poll` this phase introduces.

**Architecture:** The waiting primitive is one function, `wait(input, wake, timeout)`,
with a POSIX backing (`poll`) and a Windows backing (`WaitForMultipleObjects`). Two
callers use it: the capability probe, which waits up to 50 ms for a terminal reply
and takes silence for an answer, and the loop, which waits on stdin and a self-pipe
until the next render deadline. The bus and the scheduler are pure and live in
`tugcore`, so `wasm32-freestanding` stays green; the loop, the waker, and the
cross-thread queue need file descriptors and threads, so they live in `tugshell`.

**Tech stack:** Zig 0.16.0, pinned via `minimum_zig_version` in `build.zig.zon`. No
third-party dependencies. Raw syscalls through `std.posix` and `std.posix.system` on
POSIX; `kernel32` externs on Windows, in the style `src/shell/term/windows.zig`
already uses.

### Zig 0.16 API notes

Facts established by reading the pinned standard library, so no task has to guess:

- `std.posix` in 0.16 has no `pipe`, `close`, or `write`. It has `read`, `poll`,
  `errno`, and `system`, which is `std.os.linux` when libc is not linked and `std.c`
  otherwise. `pipe`, `close`, and `write` are reached through `posix.system.*` and
  checked with `posix.errno`, which is what `src/shell/term/posix.zig` already does
  for `ioctl` and `write`.
- `posix.poll(fds: []pollfd, timeout: i32) PollError!usize`, `timeout` in
  milliseconds, `-1` for indefinite. `posix.pollfd` is
  `extern struct { fd: fd_t, events: i16, revents: i16 }` and `posix.POLL.IN` is the
  readable bit.
- `posix.poll` retries internally on `EINTR`. A `SIGWINCH` arriving during the wait is
  therefore not returned to the caller — but the handler has already written to the
  wake pipe by then, so the retried `poll` returns immediately with the wake end
  readable. The signal is never lost; it just arrives one syscall later.
- `std.Io.File.Reader.interface.peekGreedy(1)` blocks until at least one byte exists.
  After `wait` reports readable it returns immediately, which is why the existing
  reader is reused rather than replaced with a raw `read`.

- Produces:

```zig
// src/shell/loop/wait.zig
pub const Handle = @import("../term/backend.zig").Handle;

/// Which of the two handles became readable. Both false means the timeout
/// expired with nothing ready.
pub const Ready = struct {
    input: bool = false,
    wake: bool = false,
};

pub const Error = error{Unexpected};

/// Blocks until `input` or `wake` is readable, or `timeout_ms` elapses.
/// A null timeout blocks indefinitely — this is what makes idle cost 0 % CPU.
pub fn wait(input: Handle, wake: ?Handle, timeout_ms: ?u32) Error!Ready;

/// The loop's doorbell. `wake` is async-signal-safe and may be called from any
/// thread; everything else runs on the loop thread.
pub const Waker = struct {
    pub fn init() Error!Waker;
    pub fn deinit(self: *Waker) void;
    /// The handle to pass as `wait`'s `wake`, and to hand to
    /// `Backend.setWakeHandle` — on POSIX the SIGWINCH handler writes here.
    pub fn readHandle(self: *const Waker) Handle;
    pub fn writeHandle(self: *const Waker) Handle;
    pub fn wake(self: *Waker) void;
    pub fn drain(self: *Waker) void;
};

// src/shell/term/backend.zig — added to Backend
/// The handle to wait on for input readability.
pub fn handle(self: *Backend) Handle;
```

**Design notes the implementer needs:**

The waker coalesces. `Waker` holds `pending: std.atomic.Value(bool)`; `wake` does
`if (self.pending.swap(true, .acq_rel)) return;` and only then writes one byte. At
most one byte is ever in flight, so a 64 KiB pipe can never fill and the write in the
`SIGWINCH` handler can never block. `drain` clears `pending` **before** it reads, so
a wake racing the drain is never lost — it either wrote a byte this read will collect
or will write one the next `wait` returns for.

POSIX backing: `posix.system.pipe(&fds)` — plain `pipe`, not `pipe2`, because macOS
has no `pipe2` and the coalescing above removes the reason to want `O_NONBLOCK`.
Check with `posix.errno`. `wake` writes through `posix.system.write`; `drain` reads
through `posix.read` into a 16-byte buffer; `deinit` closes both ends with
`posix.system.close`.

Windows backing: `CreateEventW(null, 0, 0, null)` — an auto-reset event, so `drain`
is a no-op and `wake` is `SetEvent`. `wait` is `WaitForMultipleObjects` over the two
handles with `bWaitAll = FALSE`; `WAIT_TIMEOUT` (0x102) maps to an empty `Ready`, and
`WAIT_OBJECT_0 + n` sets the matching field. `readHandle` and `writeHandle` both
return the event. Declare `CreateEventW`, `SetEvent`, `CloseHandle` and
`WaitForMultipleObjects` as `extern "kernel32"` in the same style as
`src/shell/term/windows.zig`.

### Task 2: Bound the capability probe — the carried-forward defect

**Files:**
- Modify: `src/main.zig` — `probeCapabilities`
- Test: inline test in `src/main.zig`; manual reproduction under a pty

**Interfaces:**
- Consumes: `wait(input: Handle, wake: ?Handle, timeout_ms: ?u32) Error!Ready` and
  `Backend.handle()` from Task 1; `shell.modes.probe_timeout_ms` (= 50) and
  `shell.modes.kittyReplyMeansSupported` which already exist.
- Produces: no new names. `probeCapabilities` keeps its signature.

**The defect.** `src/main.zig` writes both probe queries and then calls
`terminal_reader.interface.peekGreedy(1)`, which blocks until at least one byte
arrives. The terminal is in raw mode with `VMIN=1`/`VTIME=0`, so a terminal that
answers neither query never produces that byte and `--caps` hangs forever.
`shell.modes.probe_timeout_ms` is printed at the end of the output but nothing
enforces it. Reproduced on Linux: `timeout 5 script -qec "tug --caps" /dev/null`
exits 124 with no output at all.

**The fix.** Wait before every read. Accumulate replies into a local buffer until
either both markers have been seen or the 50 ms budget is spent, then answer from
whatever arrived. Silence stays a valid answer meaning "unsupported", which is what
the existing `catch return .{}` arms already assume.

- [ ] **Step 3: Implement.** Replace the body of `probeCapabilities` after the flush:

```zig
    var reply_buffer: [256]u8 = undefined;
    var reply_len: usize = 0;

    var terminal_reader = terminal.reader(io, &read_buffer);
    const deadline = std.time.milliTimestamp() + shell.modes.probe_timeout_ms;

    // A terminal that supports neither protocol answers neither query, so this
    // has to be able to come back empty. Every read is gated on `wait`, and
    // the budget is spent once — not once per query — because a terminal that
    // answers the first and not the second must not cost two timeouts.
    while (reply_len < reply_buffer.len) {
        const remaining = deadline - std.time.milliTimestamp();
        if (remaining <= 0) break;

        const ready = waiting.wait(terminal.handle(), null, @intCast(remaining)) catch break;
        if (!ready.input) break;

        const chunk = terminal_reader.interface.peekGreedy(1) catch break;
        if (chunk.len == 0) break;

        const take = @min(chunk.len, reply_buffer.len - reply_len);
        @memcpy(reply_buffer[reply_len..][0..take], chunk[0..take]);
        reply_len += take;
        terminal_reader.interface.toss(chunk.len);

        if (probeRepliesComplete(reply_buffer[0..reply_len])) break;
    }

    const reply = reply_buffer[0..reply_len];
    return .{
        .kitty_keyboard = std.mem.indexOf(u8, reply, "\x1b[?") != null and
            shell.modes.kittyReplyMeansSupported(firstReply(reply)),
        .synchronized_output = std.mem.indexOf(u8, reply, "2026;") != null,
    };
```

Delete the `ponytail:` comment above `probeCapabilities` about sharing one read
window: the shared budget is now the implementation, not a shortcut, so the note
describes nothing to upgrade.

```zig
// src/proto/events.zig
/// The catalog with its payloads. Tagged by `Event`, so the compiler enforces
/// one arm per catalog name and the two can never drift.
///
/// Slices borrow. The publisher owns the bytes and they stay valid only for the
/// duration of the `publish` call; a subscriber that needs them longer copies.
pub const Payload = union(Event) {
    session_start: void,
    input_submit: struct { text: []const u8 },
    request_start: void,
    stream_delta: struct { text: []const u8 },
    stream_end: void,
    tool_request: void,
    tool_decision: void,
    tool_result: void,
    turn_end: void,
    err: struct { message: []const u8 },
    shutdown: void,

    pub fn event(self: Payload) Event {
        return std.meta.activeTag(self);
    }
};

// src/core/bus.zig
/// Enough for v0.1's consumers — renderer, editor, session log — with room
/// spare. Exceeding it is a wiring bug, not a runtime condition.
pub const max_subscribers = 8;

pub const Subscriber = struct {
    context: ?*anyopaque = null,
    handler: *const fn (context: ?*anyopaque, payload: proto.Payload) void,
};

pub const Bus = struct {
    subscribers: [max_subscribers]Subscriber = undefined,
    len: usize = 0,

    pub fn subscribe(self: *Bus, subscriber: Subscriber) error{TooManySubscribers}!void;
    /// Delivers to every subscriber in subscription order.
    pub fn publish(self: *Bus, payload: proto.Payload) void;
};
```

**Design notes.** No allocator, no mutex, no per-event filtering. The bus runs on the
loop thread only — that is the documented invariant Phase 3's spec names, and it is
what lets the whole thing be a fixed array and a length. Cross-thread producers go
through `Queue` (Task 5), never through `publish`. Subscribers switch on the payload
themselves; a subscription filter would be a second dispatch table for eight
consumers that already have one.

### Task 4: The render scheduler

**Files:**
- Create: `src/core/scheduler.zig`
- Modify: `src/core/root.zig` — re-export
- Test: inline tests in `src/core/scheduler.zig`

**Interfaces:**
- Consumes: nothing from earlier tasks.
- Produces:

```zig
// src/core/scheduler.zig
/// ~8 ms between paints caps output at 125 frames per second no matter how
/// fast events arrive. Above that the terminal is the bottleneck and the extra
/// writes buy nothing but flicker.
pub const default_frame_ms: u32 = 8;

pub const Scheduler = struct {
    min_frame_ms: u32 = default_frame_ms,
    dirty: bool = false,
    urgent: bool = false,
    last_paint_ms: u64 = 0,
    painted_once: bool = false,

    /// Something changed and should be drawn within the frame budget.
    pub fn markDirty(self: *Scheduler) void;
    /// Something changed that must be drawn now: a stream ending, a turn
    /// boundary, a resize. Endings that wait 8 ms feel laggy in a way that
    /// mid-stream frames do not.
    pub fn markUrgent(self: *Scheduler) void;
    /// How long the caller may block. Null means "indefinitely" — with nothing
    /// dirty there is no deadline, which is what makes idle cost 0 % CPU.
    pub fn timeoutMs(self: *const Scheduler, now_ms: u64) ?u32;
    /// Whether a paint is owed at `now_ms`.
    pub fn due(self: *const Scheduler, now_ms: u64) bool;
    /// Records that a paint happened, which starts the next frame interval.
    pub fn painted(self: *Scheduler, now_ms: u64) void;
};
```

**Clock injection, and why there is no `TimeSource` type.** Every method that needs
the time takes it as a parameter. That *is* the injection the spec asks for: the tests
below pass literal milliseconds and never sleep, and the loop passes
`std.time.milliTimestamp()`. An interface with one implementation would add a vtable
and change nothing about what is testable.

```zig
// src/shell/loop/queue.zig
/// One turn of the loop drains the whole queue, so this only has to absorb what
/// arrives between two wakeups. A provider thread emitting faster than that is
/// the firehose case Phase 5 exists to test.
pub const capacity = 64;

/// Multi-producer, single-consumer. Producers are provider threads; the
/// consumer is always the loop thread.
pub const Queue = struct {
    mutex: std.Thread.Mutex = .{},
    items: [capacity]proto.Payload = undefined,
    head: usize = 0,
    len: usize = 0,

    pub fn push(self: *Queue, payload: proto.Payload) error{Full}!void;
    pub fn pop(self: *Queue) ?proto.Payload;
    /// Publishes everything queued onto the bus. Returns how many were
    /// delivered, so the loop can tell an empty wake (a resize) from a full
    /// one.
    pub fn drainInto(self: *Queue, bus: *core.Bus) usize;
};
```

**Design notes.** `drainInto` pops one item at a time and releases the mutex before
each `publish`, so a subscriber that pushes cannot deadlock against the drain. It
loops until `pop` returns null rather than snapshotting a count, which also drains
anything a producer added mid-drain.

`ponytail:` payload slices are borrowed, and a queued payload outlives its producer's
stack frame. Nothing produces `input_submit`, `stream_delta` or `err` across a thread
boundary in Phase 3 — the only cross-thread signal is a resize, which carries no
bytes. Phase 5's mock provider is the first real producer and is where ownership gets
decided: either an arena drained with the queue, or a fixed byte pool behind it. The
comment goes in the file so the decision is not rediscovered.

**The loop body, in full.** The spec says it fits on one screen and stays that way,

```zig
pub fn run(self: *Loop) !void {
    var read_buffer: [1024]u8 = undefined;
    var terminal_reader = self.terminal.reader(self.io, &read_buffer);

    // When the decoder is holding an incomplete sequence, a lone ESC has to be
    // resolved by silence. That is a second deadline, and the wait takes
    // whichever of the two comes first. Two deadlines min'd together is still
    // one time concept — the scope guard forbids a timer wheel, not arithmetic.
    var pending_since_ms: u64 = 0;

    while (true) {
        var now: u64 = @intCast(std.time.milliTimestamp());
        var timeout = self.scheduler.timeoutMs(now);
        if (self.decoder.pending() > 0) {
            const deadline = pending_since_ms + decoder_mod.escape_timeout_ms;
            const remaining: u32 = if (now >= deadline) 0 else @intCast(deadline - now);
            timeout = if (timeout) |budget| @min(budget, remaining) else remaining;
        }

        const ready = try waiting.wait(self.terminal.handle(), self.waker.readHandle(), timeout);
        now = @intCast(std.time.milliTimestamp());

        if (ready.input) {
            const chunk = terminal_reader.interface.peekGreedy(1) catch return;
            if (chunk.len == 0) return;
            if (self.decoder.pending() == 0) pending_since_ms = now;
            self.decoder.feed(chunk);
            terminal_reader.interface.toss(chunk.len);

            while (self.decoder.next()) |event| {
                if (self.handlers.onInput(self.handlers.context, event) == .stop) return;
                self.scheduler.markDirty();
            }
        }

        if (ready.wake) {
            self.waker.drain();
            // An empty wake is a resize: SIGWINCH writes to the same pipe and
            // carries no payload. Resizes repaint now, not in 8 ms.
            if (self.drainQueue() == 0) self.scheduler.markUrgent();
        }

        if (!ready.input and !ready.wake and self.decoder.pending() > 0) {
            if (self.decoder.flushPending()) |event| {
                if (self.handlers.onInput(self.handlers.context, event) == .stop) return;
                self.scheduler.markDirty();
            }
        }

        if (self.scheduler.due(now)) {
            try self.handlers.onRender(self.handlers.context);
            self.scheduler.painted(now);
        }
    }
}

fn drainQueue(self: *Loop) usize {
    var delivered: usize = 0;
    while (self.queue.pop()) |payload| {
        switch (urgency(payload.event())) {
            .urgent => self.scheduler.markUrgent(),
            .normal => self.scheduler.markDirty(),
        }
        self.bus.publish(payload);
        delivered += 1;
    }
    return delivered;
}
```

tests and for callers that do not schedule.

```zig
pub fn waitBudget(render_ms: ?u32, escape_deadline_ms: ?u64, now_ms: u64) ?u32 {
```

## Handoff

This plan is a hypothesis about work not yet done. Three places are the likeliest to
be wrong, and the executor should expect to correct rather than obey them:

- **`std.Io.File.Reader` over a handle `wait` already reported readable.** The claim
  that `peekGreedy(1)` returns immediately follows from the reader wrapping a blocking
  `read`, but the 0.16 `Io` layer may buffer differently than that reasoning assumes.
  If a read blocks anyway, drop to `posix.read` on the raw handle in task 6 and let
  the decoder own all the buffering.
- **`posix.system.pipe` on macOS.** Established for Linux by reading the pinned
  standard library; the macOS path goes through `std.c.pipe`, which is declared but
  has not been compiled here. macOS is tier-1, so a cross-compile check belongs in
  task 1's step 4 if it can be made cheap.
- **`WaitForMultipleObjects` on a console input handle** signals for non-key records
  too — focus changes, buffer-size events. The loop tolerates that (a spurious wake
  decodes zero events and paints nothing), but on Windows it may wake more often than
  the 0 % idle claim suggests. Windows is tier-2 and out of the matrix, so this is a
  note, not a gate.
